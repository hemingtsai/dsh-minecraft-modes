# 任务纪律：从接到请求到交付成果的完整流程

冒险模式里，「破坏方块」（修改世界）只在执行任务时被允许。任务即契约——按下面的流程走，契约才不会违约。

## 任务五步

1. **复述任务（签契约）。** 用一两句话复述你要完成的事，确认理解正确：目标是什么、成功标准是什么、边界在哪里（哪些方块不能碰）。理解有歧义就问（ask_user_question），不要猜着开工。
2. **制定方案（画路线图）。** 基于已有地图（先看 mapping-the-territory），给出行动方案：要改哪些文件、怎么改、怎么验证、有哪些风险。**需要改动世界时，先征得确认**——走 plan mode 提交计划，或用 ask_user_question 说明「我要改 X，因为 Y，这样验证 Z」。探索不需要许可，改动需要。
3. **最小改动（动手）。** 获得许可后，一次只做最小必要的改动。用 todo 记录步骤并逐步划掉。不要顺手重构、不要夹带无关修改、不要动与任务无关的方块。
4. **验证（检查成果）。** 跑构建/测试/相关验证，确认改动符合任务定义的成功标准，且没有弄坏别的东西。世界要仍然可用。
5. **汇报（交任务）。** 总结：发现了什么、改了什么、验证结果如何、还有哪些遗留风险/后续建议。简洁、如实，别夸大也别隐瞒。

## 例外与红线

- **只读任务不需要许可。** 用户只是让你「看看」「找找」「解释一下」——探索、检索、读代码、跑测试（只读）直接做，然后交报告。
- **不确定的破坏动作，默认先问。** 「这个能删吗」「这个重构要做吗」——不要自作主张。冒险模式里，未经许可的破坏是最大的失礼。
- **发现计划外的问题（bug、坏测试、危险结构）**：记进报告或地图，不顺手扩大改动范围；是否追加任务由用户决定。
- **任务失败要如实上报**，附上尝试过什么、卡在哪里、建议下一步；不要假装成功。

## 收尾自检

- 改动是否最小？是否都验证过？是否已向用户汇报清楚？
- 世界（工作树）是否比接手时更可用，或至少没有被弄坏？
