# 绘制地图：把陌生代码库变成一张可以交给别人的地图

冒险模式的第一准则：先绘制地图，再谈行动。地图是探索的产物，也是行动的许可证——你（和用户）要先看得见世界，才谈得上改世界。

## 测绘流程

1. **从制高点俯瞰。** 先读清单与文档：`package.json` / `pyproject.toml` / `go.mod` / `Cargo.toml`、`README*`、`docs/`、`CONTRIBUTING*`。这些是地图的图例：生态、脚本、约定、入口。
2. **标注地标（入口与骨架）。** 找到 main / 入口文件 / 路由注册 / 初始化流程，沿调用链把主干画出来。记下每个关键模块：负责什么、被谁调用、依赖谁、有没有测试。
3. **点亮火把（构建与测试）。** 确认构建、测试、lint 命令并实际跑一次测试，记录基准状态（是否本来就绿）。这是后续判断「世界有没有被我弄坏」的参照系。
4. **标记危险区。** 明显的技术债、奇怪的架构、没有测试的模块、神秘的全局状态——在地图上标红，报告给用户，而不是擅自深入或重写。
5. **成图交付。** 把地图整理成一份简短报告（或 `.notes/` 下的地图文件）交给用户：结构总览、关键文件清单、验证命令、风险清单、建议的行动路线。先交图，再等任务。

## 测绘的纪律

- **探索永远免费，但也别无限期免费。** 地图够支撑「下一步行动」就可以停；别把整个仓库读完才肯动身。
- **用搜索精确定位，别全文漫游。** 明确了目标区域后用 grep/glob 精准落点，效率与准确度都更高。
- **地图要可复用。** 把结论写进文件（用户可回读），而不是只存在对话里——冒险者的地图要能带回来。

## 产出

一张能回答三个问题的地图：世界长什么样？怎么验证改动？哪里最危险？把它交给用户，然后才开始考虑任务。
