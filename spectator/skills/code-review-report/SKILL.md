# 审查报告：把发现整理成可以行动的报告

审查的价值在于别人能**照着报告行动**。报告不是流水账，是一张分级的问题地图。

## 报告结构

1. **审查范围**：审了什么（文件/提交/模块）、审查方式（读了什么、搜了什么、对照了什么）。
2. **全局图景**：3–6 句的世界观——项目结构、入口、数据流、明显风险区。让读者（可能不熟这块代码）能跟上后续问题。
3. **问题清单**（核心），每条含：
   - **严重程度**：阻断（Blocking，会导致错误/破坏/安全）／重要（Major，明显缺陷）／建议（Minor，可改进）。
   - **位置**：文件 + 行号（或符号名），可复现路径。
   - **证据**：为什么这是问题——引用代码、测试、文档；区分「事实」（直接看到）与「推断」（推演得出）。
   - **建议**：怎么改，附风险与工作量估计（一句话级别）。
4. **总体结论**：这块代码/这次变更是否可接受；放行的前提条件是什么；值得称赞的地方也如实写。

## 纪律

- **先建图，再细看**：先扫清单/入口/测试建立图景，再逐项深入；不要一上来就逐行读。
- **清单作业**：用 todo 列出待查方面（正确性、边界/错误处理、性能、安全、可维护性、测试覆盖），逐项划掉，避免漏项。
- **一条问题一条证据**：没有证据的问题降级为「疑点」或「询问」，不要写成事实。
- **宁缺毋滥**：拿不准的放进「疑点/待确认」小节，不虚报严重程度。
- **不修复**：所有建议都是文字；动手的事交给其他模式。
